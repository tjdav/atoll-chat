# i18n Plugin Usage Guide

## Prerequisite: `defineComponent`

- **The Rule:** Every component's `<script type="module">` block MUST `import { defineComponent } from 'coralite'` and `export default defineComponent({ ... })`.
- **Consequence of Omission:** Without the `defineComponent` wrapper, Coralite's build-time AST compiler silently drops the `client()` block from emitted client bundles and omits the page-level runtime loader script. The build succeeds silently, but hydration never runs, leaving `<c-token>` placeholders empty and component scoped CSS unapplied.
- **Enforcement Test:** Repository-wide assertion at `packages/app/tests/unit/components-defineComponent.test.js`.
- **Evidence:** Documented in `client-verification.md` under the `C-V-F` entry.

## 1. Overview

The `i18n` plugin provides internationalization, locale detection, and reactive translation capabilities across `@atoll/app`. It exposes an isolated translation engine in both server/SSR and client contexts, allowing components to render localized text on initial paint and reactively update when the active locale changes.

## 2. Contract

### Server Context (`ctx.i18n`)

Delivered strictly to `server()` blocks during server-side rendering / static extraction.

- `t(key: string, vars?: Record<string, unknown>): string` — Translates a key with optional variable interpolation.
- `getLocale(): string` — Returns the current active locale code (e.g. `'en'`).
- `strings(keys: string[]): Record<string, string>` — Translates an array of keys and returns a key-value object map.

### Client Context (`ctx.i18n`)

Delivered strictly to `client()` blocks in the browser.

- `t(key: string, vars?: Record<string, unknown>): string` — Translates a key with optional variable interpolation.
- `getLocale(): string` — Returns the current active locale code.
- `setLocale(locale: string): void` — Updates active locale, persists to `localStorage` (`atoll.preference.locale`), and notifies subscribers.
- `strings(keys: string[]): Record<string, string>` — Translates an array of keys and returns a key-value object map.
- `subscribeLocale(cb: (locale: string) => void, opts?: { signal?: AbortSignal }): () => void` — Subscribes a listener callback to locale changes. Supports optional `AbortSignal` for automatic cleanup on component disconnect.

## 3. Component Pattern

All components with user-facing strings MUST use the four-part pattern:

1. **Underscore Key Format.** All translation keys use valid JS identifiers with underscores (e.g. `auth_login_title` instead of dot notation `auth.login.title`). This ensures Coralite's build-time AST static analyzer can track state property dependencies on `state`.
2. **`server({ i18n })` seeds state.** Spreads `i18n.strings([...])` and `locale` into component state.
3. **Getters read from state identifiers.** Getters read `state.auth_login_title`. They do not call `i18n.t()`.
4. **`client({ state, i18n, signal })` subscribes to locale changes.** Registers `i18n.subscribeLocale` with `{ signal }`, updating `state.locale` and re-applying `i18n.strings([...])` with an inlined key array.
5. **Template binds flat getter identifiers.** Templates bind to getters using `{{ getterName }}`.

### Complete Worked Example (`auth-view-login.html`)

```html
<template id="auth-view-login">
  <section class="card">
    <header>
      <h1>{{ auth_login_title }}</h1>
    </header>
    <form ref="form" novalidate>
      <label class="field">
        <span class="field-label">{{ auth_login_username_label }}</span>
        <input ref="username" type="text" name="username" required>
      </label>
      <button ref="submit" type="submit" class="primary" disabled="{{ pending }}">{{ submitLabel }}</button>
    </form>
  </section>
</template>

<script type="module">
export default {
  attributes: {
    pending: { type: Boolean, default: false }
  },
  server({ i18n }) {
    return {
      locale: i18n.getLocale(),
      ...i18n.strings([
        'auth_login_title',
        'auth_login_username_label',
        'auth_login_submit_button',
        'auth_login_submit_pending'
      ])
    }
  },
  getters: {
    submitLabel: ({ state }) => (state.pending ? state.auth_login_submit_pending : state.auth_login_submit_button)
  },
  client({ refs, emit, state, signal, i18n }) {
    i18n.subscribeLocale((locale) => {
      state.locale = locale
      Object.assign(state, i18n.strings([
        'auth_login_title',
        'auth_login_username_label',
        'auth_login_submit_button',
        'auth_login_submit_pending'
      ]))
    }, { signal })
  }
}
</script>
```

Refer to `packages/app/src/components/containers/auth-view-login.html` for the canonical reference file.

## 4. Failure Modes

| Anti-Pattern / Failure Mode | Why It Fails |
|---|---|
| `state['auth.login.title']` bracket reads on dot keys | Coralite's build-time AST static analyzer (`analyzeFunctionBlock`) does not statically extract bracket property reads on `state`. Getter dependencies are recorded as empty, causing `<c-token>` placeholders to render empty strings. Always use valid JS identifier underscore keys (`state.auth_login_title`). |
| `client(({ t }) => ...)` flat destructure | Plugin context is namespaced under `ctx.i18n`. Flat destructuring yields `undefined` and throws `TypeError: t is not a function`. |
| `title: ({ state, i18n }) => i18n.t(...)` in getter | Getters receive strictly `{ state, root, refs, slots, signal }`. Plugin context is not passed to getters. |
| `const KEYS = [...]` at module scope referenced in `client()` | Coralite strips top-level module scope during client bundling. References to module-scope constants in `client()` evaluate as `undefined`. |
| `subscribeLocale(cb)` without `{ signal }` | Omitting `{ signal }` causes subscriber leaks when components unmount / disconnect. |
| `if (!state.locale) state.locale = ...` lazy init | Lazy state initialization causes hydration mismatches between SSR and browser initial render. |

## 5. The Known Cost

The list of translation keys MUST be declared twice in every component: once in `server()` and once in `client()`.

This duplication is a structural requirement of Coralite's serialization boundary. Module scope is stripped from client JS output, so constants declared outside component blocks cannot be shared across the `server()` / `client()` boundary.

If a key is omitted in `server()`, initial SSR html will be missing the key. If omitted in `client()`, the key will fail to update when the user switches locales.

## 6. Adding a New Key

1. Add the English string to `packages/app/src/lib/i18n/locales/en.js` using underscore identifier key format (`group_section_name`).
2. Add the key and translated string to all six other locale files (`fr.js`, `de.js`, `ja.js`, `pt.js`, `it.js`, `es.js`).
3. Add the key string to the `i18n.strings([...])` array in `server()` of any component that uses it.
4. Add the key string to the inlined `i18n.strings([...])` array in `client()` of the same component.
5. Add a getter reading `state.group_section_name`.
6. Bind the getter in the component template `{{ getterName }}`.
7. Run the parity check test (`pnpm test:batch unit-smoke`).

## 7. Adding a New Locale

1. Create `packages/app/src/lib/i18n/locales/<code>.js` exporting a default dictionary object matching the complete key set of `en.js`.
2. Import and add the new locale dictionary to `packages/app/src/lib/i18n/locales/index.js`.
3. Add the locale code string to `SUPPORTED_LOCALES` in `packages/app/src/lib/i18n/constants.js`.
4. Run unit and parity tests to confirm 100% key parity.
